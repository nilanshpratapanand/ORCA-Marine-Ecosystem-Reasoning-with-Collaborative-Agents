# ORCA Contracts — Read This Before Writing Any Code

This file defines the exact "shape" every piece of data must have when it moves between parts of the system.
Every agent, every API call, every database table follows the format below — no exceptions, no improvising.
When asking an AI to write a new file, paste the relevant section below into the prompt.

---

## 1. API Contract — Frontend ↔ Backend

### Request: Frontend sends this to `POST /query`

```json
{
  "query": "Is it safe to fish near Kochi tomorrow?",
  "role": "fisherman",
  "session_id": "abc123"
}
```

| Field | Type | Meaning |
|---|---|---|
| `query` | string | The user's raw question, typed as-is |
| `role` | string | One of: `"fisherman"`, `"researcher"`, `"disaster_ops"` |
| `session_id` | string | Random ID generated by frontend on first load — used to remember conversation context |

### Response: Backend sends this back

```json
{
  "answer": "Sea conditions near Kochi look moderate tomorrow. Wave height ~1.2m, no advisory issued.",
  "confidence": "high",
  "sources": ["INCOIS Ocean State Forecast", "MOSDAC SST"],
  "agents_used": ["orchestrator", "data_retrieval", "fisheries_safety"],
  "data_last_updated": "2026-08-23T06:00:00Z",
  "map_data": { "lat": 9.93, "lon": 76.26, "region": "Kochi coast" }
}
```

| Field | Type | Meaning |
|---|---|---|
| `answer` | string | The final text shown in the chat |
| `confidence` | string | `"high"`, `"medium"`, or `"low"` — shown in the UI so the user knows how much to trust it |
| `sources` | list of strings | Which datasets backed this answer — always show this, never omit |
| `agents_used` | list of strings | Which agents fired — used by AgentTraceViewer for the demo |
| `data_last_updated` | string (ISO date) | When the underlying data was last refreshed — used to show "stale data" warnings |
| `map_data` | object or null | Coordinates to plot on the map, if relevant. `null` if the query has no location |

## 2. Agent-to-Agent Contract — Orchestrator ↔ Specialist Agents

### What the Orchestrator sends to any specialist agent (Data Retrieval, Reasoning, Domain Advisory)

```json
{
  "task_id": "task_001",
  "query_type": "fishing_safety",
  "region": "Kochi coast",
  "date_range": {
    "start": "2026-08-23",
    "end": "2026-08-30"
  },
  "role": "fisherman"
}
```

| Field | Type | Meaning |
|---|---|---|
| `task_id` | string | Unique ID so the Orchestrator can match responses back to requests |
| `query_type` | string | One of: `"fishing_safety"`, `"disaster_risk"`, `"research_stats"`, `"general_forecast"` |
| `region` | string | Place name or coordinates |
| `date_range` | object | `start`/`end` dates in `YYYY-MM-DD` format |
| `role` | string | Same values as the API contract — passed through so agents know how to frame their answer |

### What any specialist agent sends back to the Orchestrator

**On success:**
```json
{
  "task_id": "task_001",
  "status": "success",
  "data": {
    "sst": 28.4,
    "chlorophyll": 0.6,
    "wave_height_m": 1.2
  },
  "source": "INCOIS",
  "last_updated": "2026-08-23T06:00:00Z"
}
```

**On failure (this is not optional — every agent MUST handle this case):**
```json
{
  "task_id": "task_001",
  "status": "error",
  "reason": "no_data_for_region",
  "message": "No cached data available for this region/date range"
}
```

| Field | Type | Meaning |
|---|---|---|
| `status` | string | `"success"` or `"error"` — the Orchestrator checks this first, always |
| `reason` | string | Only present on error. Machine-readable code, e.g. `"no_data_for_region"`, `"stale_cache"`, `"timeout"` |
| `data` | object | Only present on success. The actual values — field names vary by agent, but must be documented here when added |
| `source` | string | Which dataset/system this came from |
| `last_updated` | string (ISO date) | When this specific data was fetched — the frontend uses this to show freshness |

**Golden rule:** if an agent doesn't have real data, it returns `status: "error"` — it must NEVER invent a plausible-looking number. This is what "insufficient data honesty" means in the proposal doc.

## 3. Database Schema — What Gets Stored

### Table: `ocean_readings`
Stores the actual environmental data pulled from MOSDAC/INCOIS.

| Column | Type | Meaning |
|---|---|---|
| `id` | integer, primary key | Auto-generated row ID |
| `region` | text | Place name, e.g. `"Kochi coast"` |
| `latitude` | float | |
| `longitude` | float | |
| `sst` | float | Sea surface temperature (°C) |
| `chlorophyll` | float | Chlorophyll concentration |
| `wave_height_m` | float | Wave height in meters |
| `source` | text | `"MOSDAC"`, `"INCOIS"`, or `"Bhuvan"` |
| `recorded_at` | timestamp | When this data point is valid for |
| `ingested_at` | timestamp | When our batch job pulled it in |

### Table: `ingestion_log`
Tracks whether the scheduled data-pulling jobs succeeded — this is what powers the "stale data" warning in the UI.

| Column | Type | Meaning |
|---|---|---|
| `id` | integer, primary key | |
| `source` | text | Which job ran (`mosdac_job`, `incois_job`, `bhuvan_job`) |
| `status` | text | `"success"` or `"failed"` |
| `error_message` | text, nullable | Filled in only if `status = "failed"` |
| `run_at` | timestamp | When the job ran |

## 4. Rules for Every New File

1. Every agent file receives input matching Section 2's request format and returns output matching Section 2's response format — no custom formats per agent.
2. Every agent must handle the "no data" case explicitly — check the code for a `status: "error"` path before considering a file done.
3. Field names are exact and case-sensitive. `sst` is always `sst`, never `SST` or `sea_surface_temp`.
4. If a new field is genuinely needed, add it to this file first, in a real commit, before using it in code — this file is the single source of truth for every teammate and every AI prompt.
